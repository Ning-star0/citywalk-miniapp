# 系统架构与边界

## 目标

首版围绕贵阳周末短途步行，完成6～8条经过核验的路线。每条2～6个点位；共享点位只维护一次。不使用实时客流平台、推荐模型或付费地图路径规划。

## 数据流与职责

- XML负责人工维护，XSD负责结构与基础类型约束。
- Python构建器补充跨记录业务约束，输出JSON及等价JS模块。
- services/catalog.js负责ID索引、搜索和组合筛选；页面不得自行解析XML。
- UI只绑定服务结果，不重复计算耗时。
- services/favorites.js负责本机收藏；打卡和缓存更新由成员6扩展独立模块。
- 服务器后续仅提供公开静态JSON，不保存用户轨迹、姓名、手机号或精确定位。
- 导航只打开已核验点位，坐标使用GCJ-02；不采集用户当前位置，未实现路径规划。

## 分层接口

list({keyword,district,metroStation,maxMinutes,includeDrafts}) → Route[]。
所有筛选条件同时成立；maxMinutes为0表示不限；默认includeDrafts=false。
关键词匹配路线名、摘要、商圈、地铁站、主题和引用点位名。

detail(routeId) → 展开的路线对象或null。
展开后的stop.point引用完整点位；总耗时由构建器生成，单位为分钟。

favorites.list() → 去重路线ID数组。
favorites.toggle(routeId) → 更新后的收藏布尔值；写入失败抛错，页面不得提示成功。

## 页面结构

home：首页入口与推荐样例，由成员4完善。
routes：路线列表及搜索筛选，由成员4完善。
detail：路线摘要、耗时拆分与点位顺序，由成员5完善。
mine：收藏入口与学习式项目状态，由成员6扩展打卡和数据更新。

## 当前实现与待办

已实现：最小页面结构、数据访问层、组合筛选、详情展开、本机收藏、XML/XSD构建器。
待实现：实地数据、正式视觉设计、地图导航、打卡记录、HTTPS更新、缓存失效策略、真机测试。
不提供：支付、社区内容、自动定位、真实行程轨迹上传、实时道路可达性承诺。

## 状态与兼容

schemaVersion表示契约主版本，当前固定1；datasetVersion表示内容版本。
更新必须先完成结构/引用/业务约束校验，失败不覆盖最后有效缓存。
首次无网络仍可使用随包数据。删除路线后保留旧收藏ID，界面显示已下架或过滤，但不能静默删除用户收藏。

## 架构负责人工作

其他成员不应自行改动ID规则或JSON字段；契约变更先发Issue，由成员1确认。
